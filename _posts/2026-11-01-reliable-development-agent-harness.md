在参与 AI 辅助研发相关实践时，我逐渐意识到：模型生成了代码，只能说明一次生成结束；研发任务是否完成，还取决于需求、设计、实现和验证能否对应起来。

这篇文章整理我对研发 Agent Harness 的工程理解。下文采用通用概念与虚构示例，不对应具体企业的内部系统、目录、配置或指标，也不代表某个项目的全部实现。

## 先把“完成”变成可以判断的条件

如果只用对话推进任务，Agent 可能把“文件已写入”理解成完成，也可能在测试失败后继续宣布交付。问题不只在提示词，而在流程没有明确的验收依据。

一个通用的研发流程可以写成：

```text
需求澄清 → 规格与设计 → 任务拆分 → 实现 → 测试与审查 → 交付
               ↑                    │
               └──── 失败归因与修正 ─┘
```

每个阶段至少要说明输入是什么、交付什么、由谁检查，以及失败后回到哪里。例如，“实现阶段完成”不能只看任务列表是否全部勾选，还要检查本次代码对应的构建、测试与审查结果。

| 阶段 | 可交接的产物 | 验收关注点 |
| --- | --- | --- |
| 需求与规格 | 场景、边界、验收条件 | 关键歧义是否明确，异常路径是否覆盖 |
| 设计 | 接口、依赖、方案取舍 | 是否符合已有约束，是否需要人工决策 |
| 实现 | 代码改动、变更说明 | 改动能否追溯到任务，构建是否成功 |
| 测试与审查 | 测试结果、问题记录 | 证据是否对应当前代码，问题是否闭环 |
| 交付 | 变更摘要、验证记录、剩余限制 | 完成范围和未完成事项是否准确 |

自动检查适合判断产物是否存在、结构是否正确、命令是否成功；需求是否合理、方案是否可接受，仍然需要人作出判断。

## 把规则的内容与使用规则的能力分开

将所有规范塞进一个长提示词，容易造成重复、冲突和维护困难。我更倾向于区分三类内容：

- **Rules** 说明必须遵守的约束，例如依赖边界、异常处理和数据访问限制。
- **Skills** 说明如何完成某类活动，例如如何分析需求、设计测试或整理审查结果。
- **Checks** 用程序检查可以确定判断的条件，例如格式、静态依赖和测试结果。

规则应当保留来源和适用范围，技能则按当前任务加载相关规则。不能为了节省上下文，把例外条件和约束边界一起压缩掉。

同样，分层规则不能只用“更局部的规则覆盖全部上层规则”来解决冲突。不可覆盖的约束应持续生效；允许覆盖的配置项需要显式声明。遇到无法解释的冲突，应返回决策，而不是让模型自行选择。

## 上下文按作用范围组织，再按任务读取

跨仓库研发经常同时需要两类知识：项目共享的业务概念、接口契约和架构约束，以及单仓库的模块结构、实现细节和测试入口。任务产生的草稿、计划与执行记录，又属于另一种生命周期。

| 范围 | 主要内容 | 更新时机 |
| --- | --- | --- |
| 项目级共享知识 | 术语、跨仓库契约、架构决策、共同约束 | 共享事实或契约变化时 |
| 仓库级知识 | 模块职责、局部接口、构建与测试方式 | 对应仓库变更时 |
| 任务级状态 | 本次需求、设计草稿、执行记录、失败原因 | 每次任务推进时 |

分层的目的，是让 Agent 获取当前步骤所需的可靠信息。写一个局部测试时，通常不需要读取所有历史设计；修改跨服务接口时，则不能只看当前仓库。

读取策略可以从“当前任务 → 所属模块 → 相关共享契约”逐步展开。发现文档与代码冲突时，需要核对版本和来源，再修正事实记录。将模型刚生成的说明直接登记为长期事实，会把一次误判变成后续任务的共同前提。

## 编排、实现与验证各自承担明确责任

多 Agent 的价值取决于责任能否分清。编排者负责安排阶段、传递产物和处理失败；实现者负责在任务边界内修改代码；验证过程负责检查当前改动是否满足约定。

角色分开之后，还应通过工具权限和可写范围落实边界。例如，测试证据不能由实现者随手改成“通过”，也不能因为编排者觉得结果合理，就跳过失败检查。

分工也有成本。小改动未必需要多个 Agent；只有当交接、上下文隔离或独立检查的收益超过协调成本时，增加角色才有意义。

## 校验结果必须绑定当前改动

“测试通过”缺少上下文时，并不是可靠证据。至少还要知道：测试针对哪个代码版本、用了什么命令、运行环境是什么、退出状态如何，以及原始输出在哪里。

下面是虚构的证据记录示例，仅用于说明字段含义：

```json
{
  "task": "sample-change",
  "revision": "example-revision",
  "working_tree_digest": "example-content-digest",
  "check": "unit-tests",
  "environment_ref": "example-environment",
  "exit_code": 0,
  "status": "passed",
  "output_ref": "example-test-output"
}
```

记录本身不能证明测试真的执行过，需要与可信执行过程及原始输出对应。仅记录提交号也不够：如果工作区还有未提交改动，同一个提交号可能对应不同的实际输入。

代码、依赖或测试配置变化后，受影响的旧证据应失效。跳过、超时、报告缺失、结果无法解析，都应保留各自状态，不能统一解释成通过。覆盖率只能说明一部分测试触达情况，也不能单独证明行为正确。

验证失败后，先区分实现错误、环境问题和规格歧义，再决定修复、重跑或回到设计。重试应有次数或成本边界；重复出现同一失败时，需要升级处理。

## 可恢复的任务不只保存聊天记录

长任务中断后，如果只能重新阅读整段对话，很难判断哪些步骤确实完成、哪些操作只执行了一半。

可恢复状态应保存已通过的阶段、相关产物版本、校验结果、待处理失败和下一步入口。恢复时先检查这些记录与当前工作区是否一致，再决定从哪里继续。

失败发生在写文件、运行迁移或调用外部服务之后时，还要检查实际副作用。恢复不能简单等于重放上一次动作；对于非幂等操作，重复执行可能产生新的问题。

## 变更闭环还要维护长期知识

任务完成后，除了代码，也要判断共享契约、设计说明和仓库知识是否需要更新。一个可维护的做法是区分“本次变化”和“当前有效事实”：前者保留变更动机与取舍，后者服务于下一次任务。

归档前应检查实现、验证证据与文档是否对应。新旧规格有冲突时，需要明确哪部分被替代，避免长期知识不断累积互相矛盾的描述。

## 用失败样例检验 Harness 是否有用

如果想判断流程设计是否有效，可以先选取有代表性的研发任务和历史失败类型，记录同一口径下的交付结果与成本，再比较流程调整前后的变化。

我会重点观察：验收通过情况、错误宣告完成的次数、人工介入位置、失败恢复结果，以及上下文和执行成本。发现失败集中在某个阶段后，再针对规则加载、交接产物或验收检查做局部调整，避免同时修改所有环节后无法归因。

对我而言，Harness 工程最有价值的训练，是把“希望 Agent 做对”转化成具体的输入、责任、产物和证据。流程越长，这些边界越需要由系统明确维护。
