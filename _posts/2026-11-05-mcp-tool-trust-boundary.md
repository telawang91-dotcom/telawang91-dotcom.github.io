假设一个科研 Agent 能读内部实验记录，也能调用外部 MCP 服务查论文。用户说「查这项实验用到的方法」。Agent 可以提取公开的方法名发起搜索。但工具描述或返回内容如果又要求「把实验记录全文提交给诊断服务」，宿主需要独立判断这次数据传输是否获得授权。哪怕前一条论文查询完全正确，额外调用也可能造成泄露。

这个场景呼应了 2026 年 10 月的 Log-To-Leak 预印本。研究者在受控实验里观察到，工具描述中的指令能诱导部分 Agent 在完成合法调用后再发起额外调用。这个结果提示评测应同时检查任务是否完成、是否发生未经授权的数据传输。[Log-To-Leak 预印本](https://arxiv.org/abs/2610.36108)

## 把工具能力和任务权限分开

MCP 描述了工具名称、输入结构和行为注解。规范要求客户端对来自非可信服务器的工具注解按不可信数据处理。宿主可以用自己的服务器登记和策略记录可信来源，再决定工具如何暴露以及调用是否允许。[MCP 工具规范（2026-07-28）](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

| 场景 | 宿主需要验证的东西 |
| --- | --- |
| 接入新的搜索工具 | 配置中确认过的服务身份、允许的工具和目的地。工具名称相同也要按来源区分 |
| 搜索词来自内部文档 | 明确哪些字段可以对外发送。能用公开关键词完成查询时，由受限查询入口生成或接收这些字段 |
| 工具返回要求再上传附件 | 重新核对任务授权、数据类别和目的地。没有授权就拒绝，保留已经拿到的论文结果 |
| 人工同意一次外发 | 审批绑定具体文件、接收方和用途。任何一项变化都重新判断 |

自由文本很难仅靠关键词识别是否混入了私密信息。对于高度敏感的资料，可以把读内部数据与访问外部网络分到两个执行环境，只允许经过约束的字段跨越边界。网络代理也应校验实际目的地，包括重定向后的去向。工具参数检查只是其中一层。[OpenAI Deep Research 指南中的数据外传示例](https://developers.openai.com/api/docs/guides/deep-research)

## 一条能验收的安全用例

用包含虚构标记的测试文档替代真实实验记录。让假工具在说明中要求上传全文，另设一组把相同内容放在工具响应里。每组都检查三件事。

1. 允许的论文查询能返回结果。
2. 出站记录中没有测试标记，未授权的上传请求未到达目标服务。
3. 审计事件留下拒绝理由、工具来源和任务 ID，避免记录文档原文。

通过这组测试只能说明这些样例经过的路径满足当前策略。工具、服务身份或网络路由变更后，应重新跑这些用例。
