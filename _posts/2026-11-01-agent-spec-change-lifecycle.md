一个研发任务可以顺利完成，但给下一次任务留下错误上下文：代码已经支持新行为，规格仍然描述旧行为，新的决定只存在于历史对话里。

这让我越来越关注任务结束时的知识维护。Agent 既要知道“这次准备改什么”，也要知道“系统现在实际上承诺什么”。前者适合用增量记录表达，后者需要维护当前有效的全量规格。

本文用虚构的导出任务说明设计思路。目录、状态、标识和检查方式均为教学示例，不是内部项目配置，也不是对某个框架现有能力的描述。

## 先区分三种不同的记录

| 记录 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| 当前规格 | 系统现在应该如何工作 | 有效行为、接口约定、边界条件 |
| 变更提案与增量设计 | 这次为什么改、准备改哪里 | 动机、变更范围、备选方案、迁移影响 |
| 执行与验证记录 | 本次是否按约定完成 | 代码版本、检查结果、失败原因、评审结论 |

三者之间需要关联，但不应互相替代。测试日志不能代替行为规格；设计草稿不能在未经确认时变成当前事实；全量规格也没必要塞入每一次失败重试的细节。

这里的“全量”指当前有效约定有一个明确入口，不要求所有内容放在一个巨大的文件里。按模块拆分，再通过索引定位，通常更便于维护。

## 一个具体变更：允许取消尚未开始的导出任务

假设原系统的约定是：导出任务提交之后不可取消。新需求希望用户在任务仍排队时取消，任务开始执行后继续沿用原规则。

规格里至少需要明确下面这些情况：

| 当前状态 | 收到取消请求 | 应发生的行为 |
| --- | --- | --- |
| queued | 首次取消 | 转为 cancelled，不再开始导出 |
| cancelled | 重复取消 | 返回已取消结果，不重复产生副作用 |
| running | 请求取消 | 返回不可取消结果，任务继续 |
| finished | 请求取消 | 返回已完成结果，不修改已生成产物 |

“增加一个取消按钮”只描述界面动作，尚未说明重复请求和状态竞争。如果任务刚好被执行器取走，取消与开始执行之间需要怎样的原子状态转换，也应在实现前明确。

## 增量记录应明确替换什么

一个模糊的增量说明可能只有：“支持取消导出任务。”它没有告诉后续 Agent，旧的“提交后不可取消”约束是否全部失效。

更清楚的记录可以写成下面的教学示例：

```yaml
change: allow-queued-export-cancellation
baseline: export-spec-v3
replaces:
  - export.cancel.unavailable
adds:
  - export.cancel.queued
  - export.cancel.repeated-request
preserves:
  - export.running.cannot-cancel
```

这份记录描述替换、增加和保留的关系。稳定的规则标识能帮助定位，但是否正确替换了业务含义，仍需结合完整规格与评审判断。

如果另一个变更已经更新了同一条规则，就应重新核对基线。机械地按最后修改时间覆盖，可能将另一项已经生效的行为丢掉。

## 把需求、任务和验证连成一条证据链

我会从验收条件向后建立对应关系：

```text
允许取消排队任务
  → 条件：只有 queued 可以变成 cancelled
  → 设计：取消与领取任务共享一致的状态转换边界
  → 任务：接口、状态更新、执行器检查、界面反馈
  → 验证：状态转换、重复请求、竞争路径、回归行为
```

如果增加了取消接口，却没有修改执行器领取任务的逻辑，任务列表可能全部勾选，行为仍然有缺口。通过验收条件反查实现和验证，比仅看“文件都存在”更容易发现这种遗漏。

对应关系还可以帮助定位返工范围：规格没有变，只是实现有错，就修实现；验收条件本身遗漏了竞争行为，则需要回到规格与设计，而不是让测试 Agent 猜测产品应该怎样工作。

## 归档是一次受控的事实更新

变更通过验收后，我会按下面的顺序维护知识：

1. 确认采用的规格和设计版本，与最终实现、验证记录一致。
2. 将增量中的新增、替换和删除合并到当前规格，消除新旧约定冲突。
3. 更新受影响的接口说明、共享知识索引和示例。
4. 记录变更与代码版本的关联，再归档提案、评审和执行历史。

归档后的当前规格应直接回答“现在是否能取消导出任务”，而不要求 Agent 遍历多个历史目录才能拼出答案。

这里还需要明确“当前”的目标版本。变更合并进主分支，不等于所有部署环境都已经发布；如果系统同时维护多个版本，应保留规格与发布版本的对应关系，避免把未来行为当成线上事实。

## 中断恢复和并行变更都会挑战知识一致性

如果实现完成后、规格合并前发生中断，恢复时应能看出知识更新尚未完成。否则代码任务会被标为成功，而下一次任务仍拿到旧规格。

并行任务则有另一类风险：两个 Agent 都从同一基线生成新版本，后写入的一方覆盖前一方。可以在写入前核对预期基线，发生变化时重新合并；但文本没有冲突，也不能证明语义没有冲突。两个变更分别允许和禁止同一种状态转换时，需要明确决策。

因此，知识更新至少需要版本核对、变更关联和语义审查三部分。把所有文档放进共享目录，只解决了可访问性，还没有解决一致性。

## 自动化检查能帮到哪里

有些问题适合机械检查：规则标识是否存在、引用能否定位、基线是否改变、规格与实现是否绑定到同一版本、验证记录是否过期。

有些问题则不能只靠结构判断：新规格是否自相矛盾，用户真正需要的行为是否得到满足，迁移是否能被接受。可以让 Agent 提供检查线索，但保留需要人判断的语义取舍。

判断这套维护机制是否有用，可以观察后续任务是否减少了使用旧规则、重复澄清和返工，而不只是统计新增了多少文档。规格应当降低下一次任务的理解成本；如果每次都必须读更长的历史，它的组织方式就值得重新审视。

## 对 Harness 设计的启发

研发闭环可以从“需求 → 实现 → 测试”进一步延伸为“需求 → 规格 → 实现 → 验证 → 当前知识更新”。最后一步决定了前一次任务的成果能否成为下一次任务的可靠起点。
