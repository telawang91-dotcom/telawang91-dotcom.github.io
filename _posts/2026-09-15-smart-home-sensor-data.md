智能家居里的一个常见误区，是把所有传感器原始值直接丢给模型。这样做看起来简单，但真实环境中的温湿度、人体存在、门窗、空气质量等数据会出现抖动、延迟、缺失和冲突，模型很容易被瞬时噪声带偏。

## 第一层：先做数据有效性检查

感知层首先判断数据是不是“能用”。常见检查包括：

- 时间戳是否过期；
- 数值是否越过物理合理范围；
- 是否连续长时间不变化；
- 是否出现突发跳变；
- 多传感器之间是否明显矛盾。

异常数据不应该被静默接受，而应该带上质量标记进入后续流程。

## 第二层：处理抖动，而不是追着每个点跑

温湿度类数据通常不适合按单点决策。更稳妥的是使用滑动窗口、指数平滑或趋势特征。

例如系统真正关心的往往不是：

> 这一秒温度是 27.9 还是 28.1？

而是：

> 最近 10 分钟整体是在升温，还是只是一次瞬时波动？

因此送给预测或决策模块的应该是**状态摘要**，而不是毫无压缩的原始流。

## 第三层：不同数据走不同策略

连续变量和离散事件不能用同一种过滤方法。

温度、湿度适合平滑和趋势提取；人体存在、门窗状态更适合做去抖和持续时间判断；烟雾、跌倒等高风险信号则不能因为“平滑”而延迟关键告警。

所以数据处理策略必须与业务风险绑定。

## 第四层：多传感器冲突要显式表达

如果人体传感器显示“无人”，但床垫压力或活动数据又显示有人，系统不应该强行挑一个值相信。

更好的方式是把冲突写入状态：

```text
presence_conflict = true
confidence = medium
sources = [motion_sensor, bed_sensor]
```

然后由安全策略决定：是继续观察、请求更多证据，还是进入保守模式。

## 第五层：预测模型也要看数据量

Smart Home 项目的公开实现里，预测模块会根据历史数据量选择不同方法：数据足够时用 Holt-Winters，数据较少时退化到 Holt，再少时使用 Newton Cooling 这类更简单的物理近似。这个设计的关键不是模型名字，而是**根据证据量选择复杂度**。 fileciteturn136file0L1-L2

## 最终送入 Agent 的是什么

理想情况下，Agent 看到的不是几十条原始传感器消息，而是一份结构化环境状态：

```json
{
  "temperature": 28.2,
  "humidity": 72,
  "trend": "rising",
  "presence": true,
  "data_quality": "good",
  "conflicts": [],
  "comfort_index": "warm"
}
```

这样做有三个好处：上下文更短、决策更稳定、Badcase 更容易定位。

## 核心结论

感知层不是“把数据读出来”就结束了。一个可靠 Agent 系统需要先把原始世界压缩成**经过质量判断的结构化状态**，再让模型参与更高层决策。
