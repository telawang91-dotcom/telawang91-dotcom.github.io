很多 Agent 项目在演示时都很像：用户输入一句话，模型调用几个工具，最后返回一个结果。真正拉开工程差距的，是**当输入变脏、工具失败、上下文变长、任务变复杂以后，系统还能不能解释、恢复和验证**。

这组案例不按“用了什么框架”组织，而按一个 Agent 项目从原型走向系统时必须解决的问题组织。

## 第一层：把业务问题拆成闭环

一个项目首先要回答：输入是什么，系统中间做哪些判断，输出最终落到哪里。

例如智能家居可以拆成：

```text
感知 → 预测 → 决策 → 验证 → 执行
```

科研 Agent 可以拆成：

```text
资料 / 数据 → 检索 → 分析计划 → 代码执行 → Artifact → Claim → 复现验证
```

一旦闭环清楚，后续的 Agent、Tool、数据库、评测都能找到自己的位置。

## 第二层：把 LLM 与确定性系统分开

LLM 更适合承担理解、规划、解释和不确定决策；确定性系统更适合承担权限、状态、执行、格式校验、重试、持久化和结果验证。

一个成熟项目不会把所有职责都塞进 Prompt，而会明确：

- 哪些结果必须是结构化的；
- 哪些步骤必须由代码执行；
- 哪些状态需要持久化；
- 哪些操作必须先验证；
- 哪些风险动作需要人工确认。

## 第三层：把中间产物保存下来

只保存最终回答，会让系统很难调试。

更好的做法是保存关键中间产物，例如：

```text
Plan
Tool Call
Observation
Artifact
Validation Result
Final Claim
```

这样 Badcase 才能回答“到底错在哪一层”。

## 第四层：让项目可以被评测

项目演示成功一次没有意义。真正有说服力的是有一批固定任务，能够重复执行、比较版本差异，并把失败归因。

一个可展示项目至少应该有：

- 固定输入任务集；
- 成功条件；
- Trace；
- Badcase 分类；
- 回归测试；
- 核心指标。

## 第五层：把 README 写成系统说明，而不是功能清单

好的 README 应该让陌生人快速回答五个问题：

1. 这个项目解决什么问题？
2. 系统架构是什么？
3. 最核心的工程难点是什么？
4. 怎么启动？
5. 怎么证明它不是一个 Prompt Demo？

因此我更倾向于展示架构、闭环、验证、真实截图和可运行路径，而不是堆大量模型名和技术名词。

## 这组 Case Study 会怎么展开

接下来的章节会用 Smart Home、ReproLab、GUI Agent，以及几类脱敏后的 Agent 工程实践，分别讨论：

- 传感器数据如何进入 Agent；
- Provenance 为什么是可信系统的核心；
- Planner / Executor / Critic 如何划分边界；
- GUI Agent 如何把页面空间变成可检索结构；
- Badcase 如何从一次失败变成数据资产；
- 结构化 Plan 为什么方便执行和评测；
- Harness 如何把 Workflow、Context 和 Evaluation 串起来。

项目真正的价值，不是证明“我调用过一个大模型”，而是证明：**我知道怎么把不确定的模型能力装进一个可控的工程系统。**
