设想 Coding Agent 已通过审批，向测试服务发布一版配置。服务端写入成功，但客户端在收到回执之前断线。工作流恢复时，最后一个检查点仍显示「准备发布」。如果按它直接重跑，可能重复写入。这里需要同时回答两个问题：流程停在哪一步，以及外部服务实际做了什么。

LangGraph 的检查点可以保存流程状态。用 `interrupt()` 等待审批时，恢复执行会从被中断节点的开头重新进入。节点中位于中断点之前的副作用因此也需要考虑重入。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence) · [LangGraph Interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 把审批、提交和核对分开

1. **先冻结待审批的动作。** 保存目标环境、配置摘要、当前版本和预期变更。等待审批的节点只读取这份记录。恢复时核对审批人与动作范围，检查配置和目标环境有无变化。
2. **执行前保存操作编号。** 为同一个逻辑动作持久化一枚幂等键。重试沿用原键和请求内容。改变目标或载荷后，按新动作重新判断授权并分配新键。
3. **写入后核对实际状态。** 如果服务支持幂等键，用同一编号查回执或在协议保证的范围内重试。只有读回状态、版本或服务回执符合预期，才记为完成。

| 恢复时看到的证据 | 处理方式 |
| --- | --- |
| 已有成功回执，目标版本也匹配 | 补记本地完成状态，继续后续步骤 |
| 回执未知，目标服务能对同一个键去重 | 在幂等保证仍有效时，按同一个键重试 |
| 回执未知，服务既不能去重也查不到操作结果 | 保留「结果未知」，交给人工核对 |
| 审批后目标版本被另一任务更新 | 暂停提交，重新生成变更并取得审批 |

只在本地保存一个 UUID 并不能让外部服务自动去重。并发恢复时，应让服务端对同一个动作键去重，或通过目标版本的条件写入防止覆盖别人已经提交的变化。回读时如果存在并发写入，优先使用和操作编号绑定的回执来确认是哪次操作生效。

## 给恢复路径做一次故障注入

在测试服务成功写入后，故意让客户端收不到回执。然后从同一个任务检查点恢复两次。验收时看外部状态只发生一次预期变化、流程能补记完成状态，以及已有审批确实只覆盖原来的动作。再加一条配置被别人更新的用例，确认系统会停下来重新确认。
