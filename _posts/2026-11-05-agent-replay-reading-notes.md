读阿甘关于 Agent 可靠性的文章时，我记下了一个区分：模型输出可以作为固定输入，用来验证其后的工具和规则。要知道模型在新环境里会怎么做，还得让它重新跑任务。这比给一次失败笼统地打上「Agent 不稳定」更容易定位下一步。 [阿甘的博客 · 可靠性、评测与运营 agent](https://arganzheng.life/agent-reliability-evaluation-and-operations.html)

## 一个具体例子

设想 Coding Agent 正在修改 JSON 配置。它提交了一个带尾逗号的文件，旧版校验器误判通过，下一步准备交付。这里至少有两个要分开查的问题。

| 要验证的改动 | 怎么验 | 结果能说明什么 |
| --- | --- | --- |
| 校验器收紧 JSON 语法 | 固定出错的文件和调用参数，用新版校验器再跑，检查是否拒绝、是否阻止交付 | 原来漏掉的错误现在能被检测 |
| Prompt 要求模型读懂校验错误并修复 | 从同一仓库快照重新启动任务，观察模型能否定位、修复并再次通过验证 | 模型在收到新反馈后能否完成整条任务 |
| 权限策略禁止写配置目录 | 用录制的写操作验证拒绝规则，再重跑任务观察模型遇到拒绝后的行为 | 分别检查权限规则和模型的恢复方式 |

如果更严格的校验器改变了工具返回值，旧轨迹最多能验证到这个分叉点。后续模型动作来自旧反馈，继续把它当成新行为会掩盖问题。

## 失败样本应该留下什么

这类回归用例至少需要初始仓库快照、任务目标、模型发出的工具调用、实际工具响应和验收条件。再给每条样本标上失败环节，复盘时就能先问「哪个条件最早被破坏」，再看最后的交付有没有通过。用于复现的文件和日志需要先去掉凭据和私有内容，外部写操作应改走测试环境。

这也给我一个整理 [研发 Agent Harness](/2026/11/01/reliable-development-agent-harness/) 笔记的办法：每写一项工程约束，就给出一条能触发它的失败用例，并写清通过条件。例如，JSON 校验失败时交付步骤必须停止。留下这条用例，下次换模型或改工作流，才知道系统还能否兑现原来的约束。
